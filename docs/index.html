Accessibility should be enforced during generation, not after.

AI tools now generate entire interfaces. But without guardrails, they ship with broken accessibility. This project fixes that at the source.

Get the prompt Learn why

The core idea

What if accessibility was a constraint during code generation, not a fix applied afterward?

AI coding tools like Cursor, Lovable, Base44, and Claude Code generate full interfaces from a single prompt. Without explicit guidance, they produce code with broken keyboard support, missing labels, and invented ARIA patterns.

This project is a single, copyable prompt. Paste it into your AI tool and it transforms the model into a cautious accessibility engineer — enforcing bounded, traceable fixes on the issues that affect real users the most.

The goal is not compliance. The goal is reducing accessibility risk at the moment code is written.

Why this matters now: As AI generates more of the web, accessibility failures will scale with it. Fixing this at the source is more effective than fixing it downstream. This is accessibility as development infrastructure, not as afterthought.

Without guardrails, AI gets accessibility wrong

Observed failure modes when asking AI tools to “fix accessibility”:

  • Compliance hallucinations

    Models claim “WCAG compliant” with no basis, creating legal risk in enterprise contexts.

  • Invented ARIA patterns

    Models fabricate ARIA roles and attributes that don’t exist in any specification.

  • Runaway refactors

    What starts as an accessibility fix becomes a full UI redesign, breaking working code.

  • Design system damage

    Models aggressively change brand colors for contrast, ignoring intentional design decisions.

  • Scope creep

    Fixes for a login form cascade into typography changes, icon swaps, and global updates.

  • Overconfident output

    No distinction between verified fixes and best-effort guesses. Everything presented as certain.

How the enforcement loop works

A controlled remediation protocol. Not an autonomous refactor engine.

  1. 1

    Select enforcement mode

    Choose Basic-Safety, Public-Facing, or Enterprise-Critical. The AI refuses to proceed without a declared mode — no guessing your risk context.

  2. 2

    Identify critical flows

    The AI identifies 1–3 critical user flows (login, checkout, onboarding). All fixes are scoped to components in those flows only.

  3. 3

    Evaluate 9 risk categories

    Keyboard access, focus management, labeling, semantics, forms, structure, reflow, contrast, complex widgets — ranked by real-world impact.

  4. 4

    Apply bounded fixes

    Maximum 4 files per run. No global refactors. Stops after each batch and waits for your go-ahead. Staged commits, not autonomous rewrites.

  5. 5

    Produce traceable output

    Issues with WCAG Success Criteria references. Summary of fixes applied. Prioritized backlog of remaining risks. Audit-grade documentation.

Before and after

Three enforcement modes

The right level depends on your context. The AI won’t proceed without an explicit choice.

  • Basic-Safety

    Internal tools

    Minimal exposure. Fixes keyboard traps, missing labels, critical semantic gaps. For admin dashboards and low-risk interfaces.

  • Public-Facing

    Public websites

    Moderate exposure. Adds focus management, structure, reflow checks. For marketing sites, SaaS products, and broad-reach interfaces.

  • Enterprise-Critical

    Regulated products

    Full enforcement. WCAG citations, defensibility language, APG patterns. For procurement scrutiny and VPAT requirements.

An unexpected discovery

After running the enforcement prompt, we asked the AI to build an unrelated component: “Create a city filter dropdown.” Accessibility was never mentioned.

The generated component included ARIA combobox patterns, keyboard navigation, accessible labeling, and semantic structure — unprompted.

The prompt appears to function as session-level education. Once activated, accessibility becomes a default constraint for the entire AI session, even for unrelated tasks.

If this holds, enforcement prompts serve dual roles: remediation of existing code and preventive guidance for new code the AI writes next.

What this experiment is not

  • A guarantee of WCAG compliance
  • A replacement for accessibility testing
  • A replacement for accessibility expertise
  • An automated accessibility overlay
  • A fix for every accessibility issue
